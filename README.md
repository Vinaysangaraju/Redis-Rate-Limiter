# Redis Rate Limiter

A production-oriented **Redis-backed rate limiting system built with Flask and Python**.

This project implements a **sliding-window rate limiter** using Redis sorted sets and an atomic Lua script. It supports **role-based rate limits**, **per-client request tracking**, standard rate-limit response headers, and a **circuit breaker** that temporarily blocks IP addresses after repeated violations.

The application can be run locally or deployed using **Docker and Docker Compose**.

## Features

* Redis-backed sliding-window rate limiting
* Atomic rate-limit operations using **Lua scripting**
* Role-based request limits
* Anonymous, user, and admin tiers
* Per-endpoint and per-client rate-limit keys
* `X-RateLimit-Limit` response header
* `X-RateLimit-Remaining` response header
* `Retry-After` header when a request is rate limited
* Automatic IP blocking after repeated rate-limit violations
* Temporary circuit-breaker bans
* Redis key expiration to prevent unnecessary memory usage
* Redis connection configuration through environment variables
* Automated tests using `pytest` and `fakeredis`
* Async benchmarking using `aiohttp`
* Docker and Docker Compose support
* Gunicorn production server configuration

## How It Works

The rate limiter uses a **sliding-window algorithm** backed by Redis.

For every request:

1. The application identifies the client using the request's IP address, authorization token, or role.
2. A Redis sorted set stores request timestamps for that client and endpoint.
3. Old timestamps outside the configured time window are removed.
4. The current number of requests is checked against the client's limit.
5. If the limit has not been reached, the request is allowed.
6. If the limit is exceeded, the request receives a `429 Too Many Requests` response.
7. Repeated violations eventually trigger the circuit breaker and temporarily ban the client's IP address.

The core rate-limit operation is executed through a Redis Lua script so that removing expired requests, checking the count, and recording a new request happen atomically.

## Rate Limit Tiers

The application currently defines these default tiers:

| Role      | Requests | Window     |
| --------- | -------- | ---------- |
| Anonymous | 5        | 60 seconds |
| User      | 50       | 60 seconds |
| Admin     | 500      | 60 seconds |

These tiers are configured in `app/routes.py`.

### Authentication / Role Resolution

The application determines the request tier using the following:

* `X-User-Role` header
* `Authorization: Bearer <token>` header
* Client IP address for anonymous requests

Bearer tokens beginning with `admin-` are treated as admin requests, while other bearer tokens are treated as user requests.

## Circuit Breaker

The system also provides a simple IP-based circuit breaker.

When a client repeatedly exceeds its rate limit:

* Violations are counted in Redis.
* After **5 violations**, the IP is temporarily banned.
* The default ban duration is **1 hour**.
* Banned IPs immediately receive `403 Forbidden`.

Violation counters expire after 5 minutes, which prevents old violations from accumulating indefinitely.

## API Endpoint

### `GET /api/tier-endpoint`

Example successful response:

```json
{
  "message": "Access granted to tiered endpoint."
}
```

Example rate-limit response:

```json
{
  "error": "Too Many Requests",
  "message": "Rate limit exceeded for anonymous tier."
}
```

Example blocked response:

```json
{
  "error": "Forbidden",
  "message": "IP temporarily blocked due to malicious activity. Try again later."
}
```

### Rate Limit Headers

Successful and rate-limited responses include:

```text
X-RateLimit-Limit
X-RateLimit-Remaining
```

Rate-limited requests additionally include:

```text
Retry-After
```

These headers are generated by the rate-limiting decorator.

### Important Files

**`app/rate_limiter.py`**
Contains the Redis-backed rate limiter, Lua sliding-window implementation, violation tracking, and IP banning logic.

**`app/routes.py`**
Contains the Flask rate-limit decorator, client identification logic, role tiers, circuit-breaker handling, and API endpoint.

**`app/__init__.py`**
Creates the Flask application and initializes the Redis client and `RedisRateLimiter`.

**`benchmark.py`**
Sends concurrent requests using `aiohttp` and reports execution time, average latency, RPS, and HTTP status distribution.

**`tests/`**
Contains tests for the sliding-window algorithm, expiration behavior, role tiers, API responses, and circuit-breaker IP blocking.

## Running Locally

### 1. Clone the repository

```bash
git clone https://github.com/Vinaysangaraju/Redis-Rate-Limiter.git
cd Redis-Rate-Limiter
```

### 2. Create a virtual environment

Windows:

```powershell
python -m venv .venv
.venv\Scripts\activate
```

Linux / macOS:

```bash
python3 -m venv .venv
source .venv/bin/activate
```

### 3. Install dependencies

```bash
pip install -r requirements.txt
```

### 4. Start Redis

Make sure a Redis server is running locally on:

```text
localhost:6379
```

The application reads Redis configuration from environment variables and defaults to Redis port `6379`.

### 5. Start the Flask application

```bash
python run.py
```

The application runs on:

```text
http://localhost:5000
```

`run.py` starts the Flask application and uses port `5000` by default.

## Running With Docker Compose

The easiest way to run the complete application is Docker Compose.

```bash
docker compose up --build
```

This starts:

* A Redis container
* The Flask application
* Gunicorn with 4 workers
* A health check for Redis

The Docker configuration exposes the application on port `5000`, while the Flask container connects to the Redis service using the Docker network.

Open:

```text
http://localhost:5000/api/tier-endpoint
```

## Testing

The project uses `pytest` and `fakeredis`, allowing the rate limiter to be tested without requiring a real Redis server.

Run all tests:


The tests cover:

* Sliding-window request limits
* Request expiration
* Remaining request counts
* `429` responses
* Role-based limits
* Circuit-breaker behavior
* IP blacklisting
* Rate-limit headers

For example, the anonymous tier is tested with a limit of 5 requests per minute, followed by a `429` response after the limit is reached.

The repository includes an asynchronous benchmark script using `aiohttp`.

## Design Goals

This project was built to demonstrate how a rate-limiting system can be implemented as a reusable backend component rather than relying only on application-level counters.

The main design goals were:

* Atomic request counting
* Distributed state using Redis
* Accurate sliding-window behavior
* Different limits for different client tiers
* Protection against repeated abusive requests
* Testability without a live Redis instance
* Containerized deployment
* Basic performance benchmarking

## Why Redis?

Redis is a good fit for rate limiting because request state can be stored in memory and accessed quickly across application instances.

Using Redis also means the rate-limit state does not have to live inside a single Flask process. Multiple application workers can share the same rate-limit data.
